# Knowledge Atlas 开发路线与验收标准

路线以“先完成端到端闭环，再扩展数据源和高级能力”为原则。当前已经完成 Mock 前端，因此下一阶段应优先建立后端数据模型和 Markdown 导入闭环。

## 当前基线

已完成：

- 项目定位、文献综述和开发步骤材料。
- 知识图谱工作台视觉原型。
- Vue 3 Mock 前端。
- 节点浏览、证据展开、筛选、时间轴和模拟问答。
- 桌面端和移动端响应式适配。
- FastAPI 应用、健康检查、请求 ID 和统一错误结构。
- 项目、Markdown 来源和排队任务接口。
- SQLAlchemy 领域模型、Alembic 初始迁移和 Docker Compose 配置。
- 后端接口测试。
- 可显式执行的 Markdown 解析、持久化分块与行号查询。
- 相同项目重复上传复用、任务幂等执行和失败重试。
- 前端真实项目创建/列表、资料上传/列表、解析/重试和原文分块分页。
- 可选后台 Worker、执行租约、中断接手和重试次数上限。

尚未完成：

- PostgreSQL 与 Neo4j 容器的实机联通验证。
- PostgreSQL 中的 Worker/API 并发、租约恢复和容器启动验证。
- 大模型结构化抽取和实体消歧。
- Neo4j 写入、混合检索和真实证据问答。
- 前端真实图谱与问答接入、实验数据和部署验证。

## 阶段一 基础工程（进行中）

目标：建立可持续开发的前后端工程和本地依赖环境。

交付物：

- FastAPI 项目骨架和健康检查接口。
- PostgreSQL、pgvector、Neo4j 的 Docker Compose 配置。
- 环境变量示例、统一日志和错误结构。
- 项目、资料、任务和知识候选的基础表结构。
- 前端 API 层、加载状态和错误状态。

当前已完成前端项目/资料 API 接入及其加载、空数据、错误和重试状态；Docker 实机联通验证仍未完成。

验收标准：

- 前后端可以分别启动。
- 后端可以连接 PostgreSQL 和 Neo4j。
- `GET /health` 返回各依赖状态。
- 前端能通过 API 创建并查询一个项目。

## 阶段二 Markdown 知识闭环

目标：完成第一条真实端到端流程。

交付物：

- Markdown 与 TXT 上传。
- 按标题、段落和列表分块并保留层级。
- 内容哈希、重复导入检测和任务状态。
- 固定 JSON Schema 的知识抽取。
- 候选实体与关系确认页面。
- 已确认知识写入 Neo4j。

验收标准：

- 上传一篇 Markdown 后能够生成候选实体和关系。
- 每条候选知识都能定位到原文片段。
- 低置信度结果不会自动进入正式图谱。
- 用户确认后，前端图谱展示真实 API 数据。

## 阶段三 检索与证据问答

目标：让系统基于个人资料回答问题并提供可核验证据。

交付物：

- PostgreSQL 关键词检索。
- pgvector 语义检索。
- Neo4j 一跳和限定关系查询。
- 固定权重的结果归一化与融合。
- LangGraph 问题分类、检索、核验和回答流程。
- 答案证据面板和证据不足状态。

验收标准：

- 代码标识符问题能够通过关键词精确命中。
- 相似问题能够通过向量检索召回。
- 决策与实现关系能够通过图查询返回。
- 回答引用的每条证据都真实存在。
- 删除证据后，系统不能继续引用该证据回答。

## 阶段四 代码与 GitHub 数据

目标：将知识来源从文档扩展到真实开发活动。

交付物：

- Java、Python、JavaScript 或项目主语言的代码结构解析。
- 文件、类、函数、方法和调用关系。
- GitHub 仓库、README、Commit、Issue 和 Pull Request 导入。
- 代码行号和 Git URL 证据定位。
- 增量更新，只重新处理变化内容。

验收标准：

- 导入一个中等规模仓库后可按文件和符号查询。
- 技术决策能够追踪到代码实体或 Commit。
- 重复导入不会创建重复来源和知识节点。

## 阶段五 时序知识与治理

目标：完成论文题目中的时序能力，并增加知识质量控制。

交付物：

- `valid_from`、`valid_to`、`status` 和 `SUPERSEDES`。
- 当前知识和指定时间点历史知识查询。
- 新旧结论的补充、冲突和替代候选。
- 冲突、证据缺失、重复和孤立知识检测。

验收标准：

- 能够展示至少一条完整的知识替代链。
- 查询当前状态不会混入已失效结论。
- 查询历史时间点能够返回当时有效结论。
- 治理检测只生成建议，不自动修改正式图谱。

## 阶段六 实验与交付

目标：形成可复现的实验结果和完整答辩材料。

交付物：

- 关键词检索基线。
- 向量 RAG 基线。
- 知识图谱混合检索实验组。
- 测试问题、标准证据和标准答案数据集。
- Docker Compose 演示环境。
- 架构图、流程图、功能截图和实验图表。

评价指标：

- Top K 证据召回率。
- 答案正确率。
- 来源引用准确率。
- 跨文档关系问题正确率。
- 历史决策追溯正确率。
- 平均响应时间。
- 用户可解释性评分。

## 建议十二周安排

| 周次 | 重点 | 可验收结果 |
| --- | --- | --- |
| 1 | 后端骨架、数据库和领域模型 | 健康检查与数据库迁移 |
| 2 | 项目、资料和任务接口 | 基础 CRUD 与上传任务 |
| 3 | Markdown 解析和分块 | 可查看原文块及来源位置 |
| 4 | LLM 结构化抽取 | 通过 Schema 校验的候选知识 |
| 5 | 人工确认和实体消歧 | 候选知识可确认与合并 |
| 6 | Neo4j 图谱写入 | 前端展示真实图谱数据 |
| 7 | 关键词与向量检索 | 两路检索服务可对比 |
| 8 | 图关系检索和融合排序 | 混合检索返回组成得分 |
| 9 | 证据问答 Agent | 回答可追溯到原文 |
| 10 | 代码或 GitHub 导入 | 至少接入一个真实仓库 |
| 11 | 时序知识、实验和测试 | 历史查询与对比结果 |
| 12 | 部署、论文和答辩准备 | 可复现演示环境和材料 |

## 风险控制

| 风险 | 控制方式 |
| --- | --- |
| 功能范围过大 | GitHub、高级治理和报告放在基础闭环之后 |
| 抽取结果不稳定 | 固定 Schema、规则校验、置信度和人工确认 |
| PostgreSQL 与 Neo4j 不一致 | PostgreSQL 为事实来源，图谱作为可重建投影 |
| 演示依赖外部模型 | 保留固定测试数据和可切换的 Mock 模式 |
| 图谱数据过多导致页面卡顿 | 按中心节点和深度加载，限制可见节点数 |
| 论文创新点不明确 | 围绕关系检索、时间过滤和证据准确率设计实验 |

## 最终完成定义

项目达到以下条件才视为毕业设计核心功能完成：

- 能从至少两类真实来源构建个人开发知识。
- 知识图谱可编辑，并能回到原始证据。
- 问答融合至少三种检索信号。
- 回答包含可核验来源，证据不足时拒绝给出确定结论。
- 至少展示一组技术知识的历史替代过程。
- 有可复现的基线对比、实验数据和评价指标。
