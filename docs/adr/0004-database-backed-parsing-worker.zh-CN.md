# ADR 0004 带执行租约的数据库解析 Worker


- 状态：Accepted（已接受）
- 日期：2026-10-17

## 背景

显式解析器和前端导入流程已经实现。排队的上传仍需操作人员启动解析，进程中断也可能让任务一直停留在运行状态。PostgreSQL 已经拥有任务状态；在抽取稳定之前，独立消息代理会增加部署范围。

## 决策

- 增加可选独立进程 `python -m app.worker`，轮询持久化的解析任务。`--once` 最多处理一个符合条件的任务后退出，用于验证或计划调用。
- Worker 限定到一个用户 UUID，默认是开发用户。只处理用户/项目边界一致的来源和有效项目。接受 `markdown_parsing` 以及旧版上传任务 `knowledge_extraction`，两者都不执行模型抽取。
- Worker 和现有显式执行接口共享执行逻辑。通过数据库条件更新、新的执行 UUID、递增尝试次数和有限租约认领任务。不引入消息代理或 API 进程内后台任务。
- Worker 消费排队任务，并恢复租约过期的运行中任务。没有租约的旧版运行任务，使用开始/更新时间作为超时基准。普通失败等待明确重试。过期任务达到配置次数上限后转为失败，避免无限重试。
- 成功和失败写入都必须由执行 UUID 和运行状态共同保护。分块、来源状态和最终任务状态在同一事务中提交。被替换的执行不能覆盖更新结果，即使旧进程稍后恢复或延迟报错。
- 保留排队/失败任务的手动执行及现有 HTTP 响应结构。运行中任务不论租约是否过期，手动接口仍返回冲突；超时恢复由 Worker 执行。

## 影响

启动 Worker 后可自动解析，不改变上传接受方式。页面可以刷新任务状态；未运行 Worker 时仍可手动操作。租约为固定时长，可配置，默认 300 秒；没有心跳或抢占式取消。仍在运行的解析器超出租约时，可能与替代执行同时计算，但只有当前执行可以持久化结果。租约应设置为长于正常解析耗时。自动尝试默认上限为 3 次；失败任务仍允许明确的手动重试，且可超出该次数。

SQLite 测试可以验证写入保护和独立会话行为，但不能证明 PostgreSQL 的竞争行为。Docker/PostgreSQL 集成仍需单独验证。未来的抽取任务可能需要心跳和不同的执行时长策略。

## 评估过的替代方案

API 后台任务无法在 API 重启后存活。对当前单用户解析功能切片来说，Celery/RQ 和消息代理会增加不必要的依赖。启动时不加区分地重置运行任务，可能抢走其他活跃 Worker 的任务，并使旧结果覆盖新结果。
