# ADR 0003 持久化 Markdown 分块并显式执行解析

[English](0003-markdown-parsing-execution.md)

- 状态：Accepted（已接受）
- 日期：2026-10-17

持久化与解析决策继续有效。采纳时“仅显式执行”和缺少恢复机制的范围，由 [ADR 0004](0004-database-backed-parsing-worker.zh-CN.md) 扩展：新增可选数据库 Worker 与租约，同时保留手动接口。

## 背景

上传已经能够持久化原始 Markdown 和排队任务。当前功能切片需要在不接入模型服务或部署任务队列的情况下，提供可复现的证据位置。

## 决策

- 将来源分块保存在 PostgreSQL，包含用户/项目/来源 UUID、原文、从 1 开始且包含两端的行号范围、标题路径和 SHA-256 哈希。在不可变来源内，分块 UUID 具有确定性。
- 支持顶层 ATX/Setext 标题、段落、列表和围栏代码。其他 Markdown 作为文本保留；这是结构化子集，不是完整 CommonMark 渲染器。
- 提供同步的开发接口 `POST /tasks/{task_id}/run`。通过原子条件更新认领排队或失败任务，提交认领后，在同一事务中写入全部分块和最终状态。重复执行成功任务返回已有结果；运行中任务返回冲突。
- 同一用户项目内，相同字节复用已有来源与任务，不受文件名影响。PostgreSQL 项目行锁串行化上传创建。不同字节创建新的不可变来源；跨项目上传保持分离。
- 将解析与知识抽取分开。来源就绪仅表示解析完成，不代表知识已抽取或确认。

## 影响

在采纳本决策时，当前服务已能观测和测试解析。上传任务保持排队，直到显式执行；尚无自动队列消费者、运行中断任务的超时恢复、完整 Markdown 语法树或增量来源版本模型。SQLite 测试验证行为，但不能证明 PostgreSQL 的锁保证。后续 Worker 与租约能力见上方 ADR 0004。

## 评估过的替代方案

进程内后台任务会让失败难以观测，也无法在重启后存活。在解析稳定前，单独引入队列/Worker 会增加部署范围；两种方式之后都可以复用同一个解析服务。此时强制添加来源哈希唯一约束，可能使包含早期重复上传的数据库无法完成迁移。
