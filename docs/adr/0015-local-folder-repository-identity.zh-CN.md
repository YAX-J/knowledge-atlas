# ADR 0015 在项目内标识本地文件夹来源仓库


- 状态：Accepted
- 日期：2026-10-19

## 背景

文件夹相对路径能帮助识别文件，但不能为重复复用或跨文件解析提供稳定范围。项目级匹配可能错误合并无关仓库中的相同文件或同名包。浏览器会提供所选文件夹的根目录名和相对文件路径，但不会提供稳定的绝对路径或 Git remote。

## 决策

- 新增 `source_repositories`，保存业务 UUID、`user_id`、`project_id`、`kind`、`name` 和时间戳。首个支持的类型为 `local_folder`。
- 通过 `POST /projects/{project_id}/repositories/resolve`，按 `(user_id, project_id, kind, 规范化根目录名)` 幂等解析本地仓库；同时提供项目仓库分页列表接口。
- 来源新增可空 `repository_id`。既有行保持未归属，不执行破坏性回填。
- 上传提交 `repository_id` 时必须同时提供规范化仓库内相对路径。桌面端逐份上传文件前会剥离浏览器路径的根目录段。
- 重复复用范围加入可空仓库身份。同一仓库内相同字节复用首次来源和任务；不同仓库中的相同字节保持为独立来源。
- Java 跨文件类型解析限定在同一仓库。旧的未归属来源只与同项目中的其他未归属来源互相解析。
- 仓库解析和重复上传检查复用现有 PostgreSQL 项目行锁串行化。

## 影响

文件夹导入现在拥有稳定业务边界，可作为后续方法解析和增量同步的基础。既有单文件和历史文件夹来源继续以 `repository_id = null` 工作，不重写任何原文或证据。

本地身份有意弱于 Git 身份。同一项目中两个根目录同名的不同文件夹会解析为同一个本地仓库，而根目录改名会生成另一个身份。Git remote URL、平台仓库 ID、分支、Commit SHA、文件删除和变更对账仍属于后续能力。同一路径的文件字节变化时，当前仍创建新的不可变来源，不会替换旧来源或自动建立 `SUPERSEDES`；因此同一 Java 包限定类型的多个已解析版本可以同时存在，跨文件解析会将其显示为歧义。

## 评估过的替代方案

- 继续把整个项目作为仓库范围：拒绝，因为无关代码树可能发生冲突。
- 保存浏览器的绝对文件夹路径：拒绝，因为浏览器无法可靠提供，而且不应保存本机私有路径。
- 现在就强制 Git 元数据：推迟，以便 GitHub 导入实现前仍可使用普通本地文件夹。
- 按既有相对路径首段自动回填仓库：拒绝，因为历史路径不一定代表单一仓库，自动重新归属可能改变去重或解析语义。
